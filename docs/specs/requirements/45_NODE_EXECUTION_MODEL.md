# Node Execution Model Requirements

## Scope
- Defines dependency-driven execution over enabled data edges.
- Defines Item/List/Tree matching, modifiers, Principal selection, and atomic output publication.
- Keeps passive `flow` authoring outside the runtime graph.

## Node Categories
- `active`: transfers, transforms, or consumes data and participates in dependency scheduling, including side-effecting and outputless sinks.
- `boundary`: active Trigger behavior that deliberately stops automatic propagation until publication.
- `passive`: excluded from execution; passive `flow` edges remain visual/authoring-only.

## Contracts
- `REQ-NODE-009`: Executable topology shall use directed `data` edges only. The model shall contain no execution, completed, failed, or On Failure ports or edges; passive `flow` edges remain authored but shall not enter compilation or scheduling.
- `REQ-NODE-010`: Port compatibility shall enforce directed source/target orientation, element-type compatibility, and declared access contracts for fixed-direction data ports. Neutral passive flowchart ports with `kind="flow"`, `data_type="flow"`, and a cardinal `side` remain the only gesture-ordered direction exception.
- `REQ-NODE-011`: Every active node shall be schedulable from its enabled upstream data dependencies, including ready isolated nodes and outputless sinks explicitly targeted by Run or Run Selected.
- `REQ-NODE-012`: Side-effecting and ordered operations shall use the same dependency model as other active nodes; ordering shall come from enabled data dependencies, explicit Trigger boundaries, or If/Stream Gate data semantics rather than hidden control queues or failure routes.
- `REQ-NODE-013`: SDK guidance shall classify nodes by active, boundary, or passive runtime behavior and shall explain element type, Item/List/Tree access, optional/default behavior, modifiers, Principal eligibility, and side effects for both QML-shell and headless clients.
- `REQ-NODE-014`: The built-in catalog shall remove `core.start`, `core.end`, `core.branch`, `core.on_failure`, and `hpc.on_status` without placeholders, add `core.trigger`, `core.if`, and `core.stream_gate`, and remove all remaining retired control ports from built-ins, integrations, MARS, Tabular, plots, and HPC.
- `REQ-NODE-015`: Execution preparation shall compile nested subnode shells/pins into a flat runtime graph while preserving node IDs used for diagnostics and UI focus. Linked-workflow resolution and unified workflow interfaces are separate planned scopes under `REQ-PERSIST-025` and `REQ-NODE-036`; they do not widen this requirement or its existing proof.
- `REQ-NODE-018`: execution preparation for QML-shell and headless Corex clients shall exclude passive nodes (`runtime_behavior="passive"`) and passive `flow` edges from compiled/runtime graphs while leaving them intact in the authored workspace document.
- `REQ-NODE-019`: Every authored and runtime edge shall carry `enabled: bool = True` and ordered `input_order`. A normal drop shall validate first and then atomically replace every existing wire at that active data input; Shift-drop shall append, and exact duplicates shall remain no-ops. Disabled wires shall remain connected, selectable, serialized, and ordered but shall contribute no dependency, path, or item. Active-data multiplicity shall not depend on `allow_multiple_connections`; that flag remains available only for passive `flow` behavior such as neutral cardinal flowchart ports.
- `REQ-NODE-023`: execution data flow shall allow stored-output adopters to replace oversized inline payloads with `RuntimeArtifactRef` values while downstream nodes resolve the referenced local file within the same run from runtime-snapshot and project artifact metadata.
- `REQ-NODE-024`: the first shipped heavy-output adopter shall remain explicit and user-controlled: `io.process_run` switches only between `memory` and `stored`, and `stored` mode stages stdout/stderr transcripts instead of adding automatic size-based switching.
- `REQ-NODE-026`: cross-process viewer execution shall keep playback and live/proxy state session-owned: `model.viewer` may publish projection-safe summaries into graph state, but live promotion, demotion, one-live arbitration, `backend_id` / `transport_revision`, and session-scoped transport lifecycle shall occur through the worker `ViewerSessionService`; project reload and worker reset shall reopen only as blocked rerun-required projection until rerun recreates live transport.
- `REQ-NODE-027`: Node execution visualization shall remain run-scoped and protocol-neutral: node lifecycle events may drive running, completion, failure, elapsed-time, and diagnostic presentation, while data wires shall never represent runtime failure or progress. Session-only elapsed/output cache facts may survive transient chrome until invalidated, but they shall add no project fields, durable result claims, or second execution-state channel.
- `REQ-NODE-031`: Excalidraw board authoring shall remain passive and execution-free for QML-shell and headless Corex clients: `excalidraw.board` nodes and their web-surface state shall be excluded from compiled/runtime execution graphs, shall not add executable data semantics beyond authored passive metadata, and shall not cause WebEngine, WebChannel, managed image import, preview export, or fullscreen editor behavior to run inside the worker execution path.
- `REQ-NODE-034`: Run shall target every active node, including ready isolated nodes and outputless sinks. Run Selected shall expand selected groups, target selected active nodes, and include their enabled upstream dependencies; explicitly selected isolated active nodes shall run. Run Upstream Chain and selected-run cache seeding shall not exist.
- `REQ-NODE-041`: Each input shall be prepared through the fixed pipeline `enabled wires -> ordered path-wise merge -> Graft -> Flatten -> Simplify -> Reverse -> Clean -> Item/List/Tree matching`. Graft shall split `P:[A,B]` into `P+0:[A]` and `P+1:[B]` and drop empty branches; Flatten shall concatenate sorted branches into root `(0)`; Simplify shall remove the longest shared prefix while retaining one path index; Reverse shall reverse items within each branch; and Clean shall remove `None` items then empty branches.
- `REQ-NODE-042`: Enabled wires shall merge by persisted `input_order`, concatenating equal paths. Tree inputs receive the complete tree without creating iterations; Item/List inputs match branches by ordinal and repeat the last branch when shorter; Item inputs match items by ordinal and repeat the last item when shorter; List inputs receive the selected complete branch during Item-driven iteration. Explicit Principal wins; otherwise selection shall use sole non-Tree input, greatest path depth, greatest sum of each path's first index, then declaration order. Conversion occurs after item selection.
- `REQ-NODE-043`: One scheduled node may invoke its plugin repeatedly for Item/List matching, but calls shall remain sequential. `ExecutionContext.target_path`, `target_iteration`, and `iteration_count` shall describe each call; outputs shall aggregate privately and publish atomically only after every iteration succeeds, then receive output modifiers and travel over edges as DataTrees.
- `REQ-NODE-044`: `core.trigger` shall expose optional Tree input and Tree output, begin with explicit EMPTY output, refresh `latest_input` from upstream settlements without auto-republishing, and publish only on click. A click shall publish the newest settled value, EMPTY, or root failure and rerun downstream until the next Trigger boundary; an unconnected click shall publish `True`, stale input shall refresh upstream before capture, and Stop or infrastructure failure shall cancel a pending capture while preserving the old publication. Publication shall remain runtime-only and reset empty on reopen, duplication, or deletion. `core.if` shall select one of two Tree inputs into a Tree result from a Boolean Item condition. `core.stream_gate` shall accept Tree stream plus numeric Item gate defaulting to zero, declare its stable dynamic output group through the node-owned `REQ-NODE-046` resolver, start with two stable persisted IDs and ordinal labels, keep at least one output, route only to the midpoint-away-from-zero selected output, fail out-of-range, publish EMPTY on inactive outputs, and insert/remove any ordinal while deleting a removed output's incident wires in the same undoable mutation.
- `REQ-NODE-047`: `core.python_script` shall execute the resolved decorator-defined `run(ctx, ...)` function using the declared inputs and controls. It shall re-resolve the applied source in the worker, pass a connected paired input in preference to its saved property, accept a mapping or existing `NodeResult`, reject undeclared output keys, and leave omitted declared outputs unset. Assignment-style `result = payload`, canvas-authored Python Script port groups, fixed aliases, and creation-time migration shall be absent; existing process-isolated timeout, logging, output validation, and sanitized-error behavior remains.
- `REQ-NODE-051`: A private generic function adapter shall execute public sync or async node functions only in an isolated process worker. It shall bind `ctx`, declared inputs in declaration order, and an immutable controls-only `settings`; pass disconnected optional inputs as `None`; resolve `port=True` overrides by input presence so falsey values remain supplied; deep-freeze nested settings while returning a defensive mutable copy from `to_dict()`; validate mapping keys and declared outputs before the existing Item/List/Tree engine validates values; settle omitted outputs EMPTY and publish explicit `None`; and collect bounded `ctx.warn` calls in sequential DataTree iteration order without duplicate log events. Trusted `ctx` services, cancellation, artifacts, handles, and renderers shall remain owned by their existing internal contracts rather than decorators, and trusted in-process execution shall reject external public function references. The existing workflow-level external Python stdio client may host the same verified worker contract when a project selects its Python executable; it is separate from plugin authoring. A plugin-selectable external runner, per-plugin interpreter, dependency installer, or runner decorator remains future and unimplemented.

## Authoring Guidance
- Declare active data ports for transforms, side effects, and sinks; use passive `flow` only for non-runtime authoring surfaces.
- Choose Item, List, or Tree from the value structure a plugin consumes or emits; do not use Python containers as implicit tree topology.
- Express order and boundaries with enabled dependencies, Trigger, If, or Stream Gate; report failure through structured runtime errors, not failure ports.
- Keep canonical type IDs stable once they are documented as public interfaces; during pre-release modernization, remove stale plugin import surfaces instead of preserving them as compatibility aliases when they conflict with function-SDK contracts.

- `AC-REQ-NODE-013-01`: SDK documentation and registry examples expose active/boundary/passive, access, modifier, Principal, optional/default, and side-effect authoring contracts.
- `AC-REQ-NODE-014-01`: Catalog tests prove all control ports and five retired node types are absent, the three replacement nodes are registered, and generated/integration catalogs declare audited access metadata.
- `AC-REQ-NODE-015-01`: Nested subnode workflows execute through the existing worker engine, and runtime failures map back to authored node IDs for scope-aware focus.
- `AC-REQ-NODE-018-01`: passive runtime-wiring and worker regressions verify passive nodes and `flow` edges never reach compiled/runtime execution graphs.
- `AC-REQ-NODE-019-01`: Graph mutation and UI tests prove validate-before-replace, Shift append, duplicate no-op, persisted order, and unchanged registry-declared passive `flow` multiplicity.
