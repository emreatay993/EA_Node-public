# Performance and Excel comparison

## Measured backends

`results/benchmark.csv` is generated by `python -m skfcalc.benchmark` on the build computer. The benchmark uses the one-node thermal model and random speed/load/temperature/flow maps.

- **Full Python solver**: all standard case objects, validation, warnings and result assembly. Runs 2,000 cases and extrapolates larger rows so the release benchmark remains practical.
- **Numba DGBB one-node**: warm, compiled array kernel for deep-groove ball bearings. It includes rolling/sliding friction, seals, oil drag and the one-node thermal iteration, but excludes four-node temperatures, installation corrections and rating-life output.
- Compilation time is deliberately excluded because it is paid once per environment/cache signature.

The exact numbers depend on CPU, Python/Numba versions, array size, thermal convergence and whether the compiled cache is warm. Use the supplied benchmark on the target workstation before sizing a production workflow.

## Relation to Excel

The package does not claim a universal Excel speed ratio. Excel performance depends strongly on workbook architecture, formula dependency chains, volatile functions, circular-iteration settings, lookup design, workbook size and processor configuration. A fair comparison requires implementing the same equations, convergence tolerance and operating map in the actual workbook, then timing full recalculation.

For a single bearing point, both Excel and Python normally appear immediate. The compiled backend becomes relevant for large speed/load maps, Monte Carlo studies, calibration loops and optimization. Compare:

1. Excel full recalculation of the completed workbook;
2. `python -m skfcalc.benchmark --output results\benchmark_target.csv`;
3. end-to-end time including CSV import/export and report generation, not only the numerical kernel.
